# Check fact-scope acceptance workload

`python3 fixtures/performance/integration-discovery/materialize.py /tmp/nm-discovery-corpus`
expands the saved JSX source into 256 modules, each containing 64 independent
component/render pairs. The immutable corpus has 10,608,384 bytes and 131,328
lines of TSX plus the selected test and imported annotated helper. It contains
131,072 JSX opening elements (four per component and four per render pair),
callbacks, filters, object spreads, configured include/exclude globs, and an
integration annotation that produces a definite policy finding.

Use the same absolute corpus path for both default-feature release binaries.
Run `check --root <corpus> --config <corpus>/configs/<policy>.yml --format json`
at `--jobs 1`, `--jobs 4`, and default jobs. `consuming` selects one test;
`broad` selects every source; `disabled` requests only import relationships rooted at every dense source module.
`sql-consuming` selects one caller whose SQL builder imports a re-exported
helper and constant through a tsconfig alias; it produces one definite OFFSET
finding in the helper. `sql-broad` selects all source extensions with an exclude
payload, exercising the all-selected fast path. Both SQL policies set `reportUnusedDisableDirectives: ignore`; `sql-audit`
retains default auditing and its required broad SQL-fact support. The dense TSX modules have no
SQL demand in the selected caller’s support closure.
Measure observer off and `--timings --verbose-timings` separately. Retain fresh
process exit statuses, complete stdout hashes, elapsed/user/system CPU and
peak RSS in balanced ABBA blocks and adjacent reverse blocks. Build/test activity must
be idle while sampling. Runtime fixtures are generated by this standalone
performance utility; behavioral tests load committed `test-cases` directly.

On Linux, run the frozen executables with
`XDG_RUNTIME_DIR=<writable-runtime> python3 fixtures/performance/integration-discovery/measure.py <corpus> <baseline> <candidate> <samples.json> <source-provenance.json>`.
The driver uses `wait4` resource usage and an unpaused monotonic wall clock,
includes process startup/reporting, and checks full stdout/exit parity. It
keeps stderr hashes and separately checks non-diagnostic stderr, excluding only
the declared timing/CPU/memory/hot-path/work lines in observer-on runs. Each
cell has 12 alternating forward/reverse blocks (24 samples per arm) followed by one
AAAA and one BBBB same-binary calibration block. Before each cell, four fresh
untimed ABBA invocations warm both executables and verify their reports. These
runs are retained separately in `.warmups.jsonl`; no duration is subtracted from
measured invocations. The driver refuses to overwrite an existing cohort and
records its own SHA-256 plus executable hashes before and after sampling.

The provenance input identifies exact revisions, compiler/features/release flags,
dependency lock digest, expected corpus SHA-256, `policies` (the six names
above), and `expectedFindings` (one `integration` finding for consuming/broad,
one `rules` finding for sql-consuming/sql-broad/sql-audit, and none for disabled). The driver records
executable hashes, platform and CPU affinity in a sidecar; verifies the corpus
digest before and after; checks expected findings/statuses and observer-off/on
report parity; and appends raw samples as JSONL before finalizing JSON per cell.

The Linux driver uses the same CPU affinity wrapper for both executables.
`NM_BENCH_AFFINITY_JSON` optionally maps jobs `1`, `4`, and `default` to CPU
lists; omitted entries use the caller's full allowed set. The sidecar records
these effective affinities. Pin both arms identically within each cell.
The driver clears `RAYON_NUM_THREADS` so default jobs uses the full allowed CPU set.
