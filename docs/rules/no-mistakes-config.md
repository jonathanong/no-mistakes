# `no-mistakes-config`

## Why and when

Enable this rule in every configured repository: stale paths and ineffective
globs otherwise make a policy appear active while silently selecting nothing.

## What it catches

It validates configuration path references, scoped project globs, full-suite
trigger paths, empty ignore/exclude patterns, and incompatible `limit` plus
`direct` groups. Findings for invalid paths and valid globs that select nothing
point to the offending configuration entry's source line. Invalid glob syntax
remains a fatal configuration error; it includes the selected config filename,
source line, field path, and rule ID when the entry belongs to a named rule
application.

`tests.playwright.navigationHelpers` contains bare or dotted callee names,
not filesystem paths. Names such as `navigateTo` and `navigation.navigateTo`
do not require corresponding files.

## Options

There are no rule-specific options or defaults. It validates the active
configuration; generic application fields only decide where config loads.

## Valid example

The project root below exists in the example tree.

```yaml
# .no-mistakes.yml
projects:
  web:
    root: web
rules:
  - rule: no-mistakes-config
    scope: repository
```

```ts
// web/index.ts
export const appName = 'web';
```

## Counterexample

```yaml
# .no-mistakes.yml
projects:
  web:
    root: apps/missing
rules:
  - rule: no-mistakes-config
    scope: repository
```

The configured project root does not exist, so the rule reports
`apps/missing` at the `root` entry's source line.

## Unknown configuration keys

The loader rejects unknown top-level keys before the rule runs. This example
reports `unknownKey` at its source line and exits with code 2. Remove the key
or use a supported configuration setting.

```yaml
# .no-mistakes.yml
unknownKey: true
rules:
  - rule: no-mistakes-config
    scope: repository
```

Collection fields such as `rules` and `projects` require a list or mapping.
Use `[]` for an empty list, `{}` for an empty mapping, or omit the field.

## Analysis

### Effort

Runs at `max` only. Configuring `effort: low` is accepted: `check` emits an analysis warning (requested effort low; effective effort max because this rule has no low implementation) and runs the rule at `max`.

### Unanalyzable inputs

Following recall over precision, nothing is silently treated as clean ([how analysis works](../../README.md#how-analysis-works)); this rule has no unanalyzable inputs because it validates the parsed no-mistakes configuration, so `options.unanalyzable` has no effect on it.

## Suppression

Fix configuration rather than suppressing it. For an intentional generated
config, use a narrowly scoped file directive in a comment-capable source. When
a `no-mistakes-config` finding has a source line, a line directive can target
that entry:

```yaml
# .no-mistakes.yml
rules:
  - rule: no-mistakes-config
    scope: repository
projects:
  web:
    # no-mistakes-disable-next-line no-mistakes-config -- generated by the deployment tool
    root: generated-at-deploy
```

Source-backed locations use the selected configuration file's actual name and
the entry line for `.yaml`, `.yml`, `.json`, and `.jsonc` inputs. A custom path
selected with `--config` is reported by that path. Programmatic or derived
values without an authoritative source position use line 1 instead of a
guessed location. Line directives suppress semantic rule findings; fatal
invalid-glob load errors cannot be suppressed.

Explicit YAML tags disable source locations for that document: typed fields
and generic rule options can interpret tagged keys differently. Findings still
report the field and rule name at line 1.

## Related rules

[`config-path-references`](config-path-references.md) checks other structured
config paths; [`structured-config-policy`](structured-config-policy.md) checks
their shape.

Lints the loaded `.no-mistakes.yml` against tracked files: schema path
fields must exist, project `include`/`exclude` globs are resolved relative to
their project root, positive full-suite trigger paths must match,
ignore/exclude globs must match something, and an
environment-level `limit` must not share a budget with a `direct` group
(issue #9440).

```yaml
rules:
  - rule: no-mistakes-config
    scope: repository
```

Counterexample: `projects.web.root` points at a directory that is not in
the tree, `projects.web.include` points outside the project root, a positive
full-suite trigger path is missing, an `exclude` glob matches nothing, or
`prePush` sets `limit`
while also listing a `direct` group.

```yaml
projects:
  web:
    root: apps/missing
testPlan:
  vitest:
    environments:
      prePush:
        limit:
          files: 10
        exclude: ["gone/**"]
        groups:
          - type: direct
```

Fix: point path fields at tracked files or directories, delete empty
globs, and move the budget onto non-`direct` groups so changed tests are
not dropped.

```yaml
projects:
  web:
    root: web
testPlan:
  vitest:
    environments:
      prePush:
        groups:
          - type: direct
          - type: dependencies
            limit:
              files: 10
```

## Limitations

Write the fields of each project directly. The loader rejects YAML merge keys
(`<<: *anchor`) in project mappings and unknown top-level key holders such as
`shared`. You can use YAML aliases on declared fields.
