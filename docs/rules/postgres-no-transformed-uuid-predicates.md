# `postgres-no-transformed-uuid-predicates`

A `projects: [<name>]` entry inherits
[`projects.<name>.postgres`](../configuration/projects.md#postgresql-scope) when
that block is set. Do not restate `importSpecifier`, `executorNames`,
`executorFactoryNames`, `executorTypeNames`, `trustedSqlTags`,
`schemaCatalogPath`, or `unanalyzableSql` on the rule. `include`, `exclude`, and
`sqlInclude` may only narrow the project scope.

Require catalog-resolved UUID columns to stay bare when they are compared in
`WHERE`, `JOIN ON`, and `HAVING` predicates. This preserves indexable
comparisons against UUID parameters or bounds.

```yaml
rules:
  - rule: postgres-no-transformed-uuid-predicates
    scope: repository
    options:
      schemaCatalogPath: db/schema.json
      sqlInclude: ["db/**/*.sql"]
      executorNames: []
      unanalyzableSql: ignore
```

## Why and when

An index on a UUID column stores UUID values. Casting the column or applying a
function changes the predicate operand, so it may no longer match an
ordinary UUID index expression. For UUIDv7 timestamps, compute a UUID range bound
before the query and compare the indexed column directly.

Enable this rule on application SQL when key lookups and range scans should use
their UUID indexes.

## What it catches/requires

The rule reports a cast or scalar function call applied to a
catalog-resolved UUID column when that transformed column is an operand of a
comparison in `WHERE`, `JOIN ON`, or `HAVING`. It covers UUID primary keys,
foreign keys, unique keys, and ordinary UUID columns, including columns with
plain indexes. The catalog's column type determines the scope; a conventional
name such as `id` does not.

The rule checks which operand contains the UUID column. Casting a parameter to
UUID or computing a bound on the other side of a comparison to a bare UUID
column is allowed. For example, `id >= fn_min_child_uuidv7($1)` leaves the
indexed column bare. Aggregate results such as `COUNT(DISTINCT id)`, `MIN(id)`,
`MAX(id)`, and `ARRAY_AGG(id)` are also allowed: they compute aggregate values
from rows rather than applying a scalar transformation to the UUID operand of
the comparison. A transformed column used only in the `SELECT` list is allowed
because it does not constrain the scan. A schema-qualified custom scalar
function such as `app.min(id)` remains reportable; matching an aggregate's
name does not establish that it is a built-in aggregate.

Aggregate value inputs are outside the row-lookup predicate: even
`COUNT(id::text)` compares a count rather than the UUID column. Aggregate
`FILTER` conditions are still predicates, so a transformation such as
`COUNT(id) FILTER (WHERE id::text = $1)` is reported at the cast.

A cast or function around a boolean comparison result leaves its UUID operands
bare and is allowed. Transformations inside that comparison remain checked.

## Options and defaults

`schemaCatalogPath` is required and must name a complete catalog generated by
`no-mistakes postgres catalog`. Only the catalog's `uuid` or `pg_catalog.uuid`
column types match; the rule does not infer the underlying type of a domain.

`sqlInclude` selects SQL files and defaults to `**/*.sql` outside a locked
project scope. `include` narrows TS/JS query files independently of `sqlInclude`;
`exclude` applies to both. Select executor imports with `importSpecifier` and
`executorNames`, or the common factory/type/tag options. Set `executorNames: []`
when checking only SQL files.

`effort` defaults to `max`. The common `unanalyzable` policy defaults to
`report`, with `advise` and `ignore` available for uncertainty. The compatible
`unanalyzableSql` alias accepts `fail`, `advise`, or `ignore`. Definite UUID
operand violations remain findings under every uncertainty policy.

## Analysis

Analysis requires a complete schema catalog at `schemaCatalogPath` and uses
its column types with parsed SQL statement facts. Relation and column
ownership must resolve to a catalog column before its type can be checked.
Qualified references resolve against the relations visible at that clause;
ambiguous names and references whose ownership or type is unknown follow
the configured unanalyzable policy rather than becoming definite violations.
The rule is catalog-aware rather than a syntax-only check: a cast
or function call is reported only when its operand resolves to a UUID column
and participates in a checked predicate.

Unsupported syntax, such as `id::text COLLATE "C" = $1`, can prevent SQL parsing
and follows the unanalyzable policy instead of producing a definite violation.
Each raw SQL parse failure points to the first code token of its failing
statement. Multiple failures keep separate locations, so a `disable-next-line`
directive immediately above a statement suppresses only that statement's
uncertainty. Independently parsed sibling statements remain analyzable.

At `effort: low`, the rule analyzes supported literal SQL directly in SQL files
and executor calls. Direct strings, interpolation-free templates, and one local
constant are supported at named executors and proven typed parameters. Exact
imported `sql-template-strings` default/`SQL` tags also qualify: interpolations
are bind values, and a local builder must have no mutation or unmodeled use.
Defaulted typed parameters, typed callbacks and immutable configured factory
bindings use the same ownership proof. Erased
type references create no findings; dynamic SQL and runtime executor escapes
are diagnosed at their own use. See [executor
bindings](../postgres-facts/executor-bindings.md).
JavaScript escapes and other construction follow the
unanalyzable policy. At `effort: max`, it also analyzes supported prepared SQL
builders and helper-returned statements. Unanalyzable or dynamic query text
follows the configured `unanalyzableSql` policy.

The rule does not inspect expression indexes or model PostgreSQL's plan
selection. It enforces the bare-UUID-operand policy even if an expression
index may support a transformed predicate; it does not claim that every
finding causes a sequential scan. SQL syntax or dynamic query text that cannot
be analyzed follows the configured `unanalyzableSql` policy.

## Valid example

```json
// db/schema.json
{
  "formatVersion": 2,
  "coverage": "complete",
  "tables": {
    "users": {
      "columns": { "id": { "dataType": "uuid" } },
      "primaryKey": { "definition": "PRIMARY KEY (id)", "columns": ["id"] }
    },
    "sessions": {
      "columns": { "user_id": { "dataType": "uuid" } },
      "foreignKeys": {
        "sessions_user_id_fkey": {
          "columns": ["user_id"],
          "referencedTable": "users",
          "referencedColumns": ["id"]
        }
      }
    }
  },
  "views": {},
  "functions": {}
}
```

```sql
-- db/queries.sql
-- The indexed key remains bare; casts and bounds are on the parameter side.
SELECT id FROM users WHERE id = $1::uuid;
SELECT id FROM users WHERE id >= uuidv7_lower_bound($1);
-- A computed bound on the other operand leaves the UUID column bare.
SELECT id FROM users WHERE id >= fn_min_child_uuidv7($1);

-- A projection can derive a timestamp without wrapping a predicate key.
SELECT uuid_extract_timestamp(id) FROM users WHERE id = $1;

-- Wrapping a comparison result does not transform its UUID operand.
SELECT id FROM users WHERE CAST(id = $1 AS boolean);
SELECT id FROM users WHERE COALESCE(id = $1, false);

-- Aggregate results operate on the group result, not as scalar wrappers on
-- the UUID column operand of a row comparison.
SELECT COUNT(DISTINCT id) FROM users HAVING COUNT(DISTINCT id) >= 2;
SELECT MIN(id) FROM users HAVING MIN(id) >= $1::uuid;
SELECT MAX(id) FROM users HAVING MAX(id) < $2::uuid;
SELECT COUNT(*) FROM users HAVING cardinality(ARRAY_AGG(id)) >= 2;
SELECT COUNT(*) FROM users HAVING COUNT(id::text) >= 2;
SELECT COUNT(*) FROM users HAVING lower(MIN(id)::text) = $1;
```

## Counterexample

```json
// db/schema.json
{
  "formatVersion": 2,
  "coverage": "complete",
  "tables": {
    "users": {
      "columns": { "id": { "dataType": "uuid" } },
      "primaryKey": { "definition": "PRIMARY KEY (id)", "columns": ["id"] }
    },
    "sessions": {
      "columns": { "user_id": { "dataType": "uuid" } },
      "foreignKeys": {
        "sessions_user_id_fkey": {
          "columns": ["user_id"],
          "referencedTable": "users",
          "referencedColumns": ["id"]
        }
      }
    }
  },
  "views": {},
  "functions": {}
}
```

```sql
-- db/queries.sql
SELECT id FROM users WHERE id::text = $1;
SELECT id FROM users WHERE CAST(id AS text) = $1;
SELECT id FROM users WHERE uuid_extract_timestamp(id) >= $1;

SELECT s.id
FROM sessions s
JOIN users u ON s.user_id::text = u.id::text;

SELECT user_id, count(*) FROM sessions
GROUP BY user_id
HAVING uuid_extract_timestamp(user_id) > $1;

-- FILTER still compares a transformed UUID column in its row predicate.
SELECT COUNT(*) FROM users
HAVING COUNT(id) FILTER (WHERE id::text = $1) >= 2;
```

## Fix

Keep the UUID column bare and cast the parameter or compute a UUID bound
before issuing the query. For timestamp ranges over UUIDv7 keys, translate the
timestamp interval to UUID bounds in application code, then compare the column:

```sql
SELECT id FROM users WHERE id >= $1 AND id < $2;
```

## Suppression

Use `no-mistakes-disable-line`, `no-mistakes-disable-next-line`, or
`no-mistakes-disable-file` for `postgres-no-transformed-uuid-predicates`.
Include a reason when an expression index or another deliberate query plan
justifies transforming a key column.

## Related rules

`postgres-generated-column-predicates` checks generated timestamp columns
