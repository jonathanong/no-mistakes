# Contributing

This repository is a huge token sink. Thus, contributions are welcomed.

1. Please add test cases as files on disk, never built inside a test:
   - New scenarios go in `test-cases/<category>/<scenario>/fixture/`. Rule pass/fail pairs go in
     `test-cases/rules/<rule>/fixture/{pass,fail}`.
   - A suite whose loader reads `fixtures/<category>/<name>/` (benchmarks, N-API, test-plan, and
     some per-rule cases) keeps its cases there. Both trees hold some `rules/`, `lockfile/`, and
     `check-runner/` cases, so find the suite's loader with `rg` and add to the tree it reads.
   - Crate-local resolver, source-discovery, and workspace cases live in readable,
     named directories under `crates/no-mistakes/fixtures/`. Load them with
     `crate::test_support::fixture_root` (available in both `no-mistakes` and
     `no-mistakes-postgres-sql`); use `materialize_saved_fixture` for an
     isolated copy before mutating files or initializing Git.

   Catalog rules listed in `SCHEMA_CATALOG_RULE_IDS` also update
   `fixtures/postgres/catalog-generation/all-rules/.no-mistakes.yml` and
   `schema.sql`, then regenerate that directory's `schema.json` on PostgreSQL 18
   (omit only the generated `currentDatabase` line). Add compliant and reported
   controls. With `NO_MISTAKES_TEST_POSTGRES_URL` set, run
   `cargo test --locked -p no-mistakes --test suite_cli_postgres postgres_catalog_real::rules`
   as well as the rule's own snapshots; the catalog inventory, generated bytes,
   complete-coverage requirement, and every-rule behavior are separate gates.

Fixture visibility must agree in Git checkouts and extracted release archives. Do not
rely on a force-tracked file overriding `.gitignore` for a shared CLI snapshot.
Keep deliberately hidden-source controls separate, and exercise fixture
materialization without Git when discovery behavior matters. Installed-package fixtures may
remain ignored by source discovery while their committed files are copied intact.

2. Rule output tests commit file snapshots. Review `.snap` and Vitest file-snapshot
   diffs like code. Rust `check --format json` snapshots use
   `crates/no-mistakes/tests/common/check_json_snapshot.rs`, which compares `--jobs 1`
   with `--jobs 2` and rewrites absolute paths, temp directories, process ids, and
   timings so the file is stable on Linux, macOS, and Windows. The helper passes
   `--lock-timeout 0` and waits for the machine-wide invocation lock. An exit 75
   lock report fails that helper instead of reading as a snapshot difference. Each finding with a
   `file` and `line` also gets `sourceLine`, the trimmed text of that fixture line
   (LF, no absolute paths; absent when the file is not a readable fixture file), so a
   finding on the wrong line shows up in the snapshot diff. CI sets `INSTA_UPDATE=no`
   and fails when a snapshot is missing or changed. The shared full Rust test
   command (`bash .github/scripts/rust-validation.sh test`) also collects
   executed snapshot references and rejects orphan `.snap` files in workspace
   packages. Remove obsolete snapshots when deleting or renaming their tests;
   filtered test runs cannot establish the full reference inventory.
   Text-format coverage for
   `agents-md-max-size` moved into that JSON snapshot: the empty pass, the
   over-limit message, the rule id, and the disabled skip. Regenerate on purpose with
   `INSTA_UPDATE=1 cargo test -p no-mistakes --test suite_cli_rules check_json_snapshot`
   or `cargo insta review`. In `packages/eslint-plugin-no-mistakes`, fixture
   diagnostics use Vitest `toMatchFileSnapshot` with relative paths and sorted
   findings. CI does not pass `-u`. Update with `pnpm exec vitest run <test> -u`
   only when that output change is intended.
3. Annotate which AI harness + model was used, `Co-Authored-By` is preferred
4. Maintain 98% project and patch test coverage

Development, CI, release builds, and benchmarks use the latest stable Rust.
Run `rustup update stable` before local validation; `rust-toolchain.toml` selects
that channel and installs Clippy and rustfmt. Workflows select `toolchain: stable`
while pinning the setup action code separately. Benchmark comparisons must use
the same resolved compiler version for both runs and record that version.

After a stable toolchain update, validate library and test targets with
`cargo clippy -p no-mistakes --all-targets -- -D warnings`, using the shared-machine
limits below. Command tests should assert their expected `ExitCode`. Preserve
short-circuit evaluation and token positions when simplifying predicates or
replacing indexed loops, then replay the affected saved fixtures and snapshots.

CI enforces per-function CRAP and cyclomatic complexity limits of 30. The
complexity gate runs `cargo crap --workspace --missing optimistic --fail-above
--threshold 30 --summary` without LCOV: assuming full coverage makes CRAP equal
cyclomatic complexity, including source omitted from the coverage report.

The optimistic check does not replace the coverage-aware CRAP gate. After a
crate-scoped coverage run, export LCOV and check the changed crate:

```sh
cargo llvm-cov report --lcov --output-path /tmp/no-mistakes-lcov.info
cargo crap -p no-mistakes --lcov /tmp/no-mistakes-lcov.info --missing skip --fail-above --threshold 30
```

Conditional framework dispatch needs fixture coverage for every supported branch,
even when its cyclomatic complexity is below 30.

Check coverage of added lines separately from whole-project coverage. Passing the
project floor does not establish the Codecov patch floor; inspect the changed
lines in LCOV and cover error diagnostics with saved invalid fixtures before
handoff. Wait for the patch check to finish after the workflow coverage job passes.

Rust lint levels live in `[workspace.lints]` in the root `Cargo.toml`; every
workspace member inherits them with `[lints] workspace = true`. CI still rejects
warnings through `RUSTFLAGS=-D warnings` and Clippy's `-D warnings` argument.
Use `#[expect(..., reason = "...")]` for a necessary local exception, and state
its invariant; fix the warning when practical. Every unsafe block states its
safety invariant in a `// SAFETY:` comment immediately before the block.

The published crate's minimum Rust version is 1.97, matching the locked OXC
dependencies. Verify it with `cargo +1.97.0 check --locked --workspace
--all-features --lib --bins`; lint validation uses the current stable toolchain.

`clippy.toml` bans type-resolved `std::time::Instant::now`, including imported
aliases. Analysis timings use the optional `InvocationObserver`; its clock
owners, compatibility adapters, deadline control clock, tests, and benchmarks
have documented expectations. The OXC parser gateway remains guarded by
ast-grep because its exact source adapter allowlist is a separate policy.
The source-policy job (`quality-source`) runs Rust validation parity tests
that exercise Clippy alias rejection and exemptions with a saved fixture. Run
the same smoke check with `bash .github/scripts/rust-lint-policy.sh`.
It uses an isolated temporary target and requires Clippy, without adding that
requirement to ordinary Rust test or coverage jobs.

Run `pnpm run lint:duplicates` to check for copied blocks of at least 30 lines
and functions with at least 80% structural similarity. CI runs the same jscpd
check and fails on any reported clone. See the [duplication guide](docs/development/code-duplication.md)
for its scope and how to fix findings.

CI retries pnpm/Node.js setup on every operating system and the coverage-shard
build-artifact download once after a five-second backoff. Each attempt has a
two-minute deadline; an exhausted retry fails the job. These retries cover
transport failures during setup, never failing tests or entire CI runs.

CI and release builds use workspace profiles with Rust debug metadata disabled;
debug assertions stay enabled. Native Rust and real-addon tests run on Windows
and macOS, while instrumented Rust coverage runs in six Linux shards and
standalone library tests run in four. These profiles are not a promise that a
job meets a particular runtime. For local debugging, use
`CARGO_PROFILE_DEV_DEBUG=2` or `CARGO_PROFILE_TEST_DEBUG=2`.

Release validation uses `.github/scripts/rust-validation.sh` for locked
workspace build, test, and documentation-test commands. The pull-request
workflow uses it for documentation tests; instrumented test targets are built
and archived once, then distributed to coverage shards. Release resumes use
validation tooling from the running workflow while retaining the tagged Rust
source; see the [CI build guide](docs/development/ci-builds.md).

CI keeps the full validation scope while running independent compiler profiles,
JavaScript policies, and test shards in parallel. Test binaries and the Linux
CLI/N-API runtime are built by producer jobs and passed to consumers as
artifacts; report jobs merge sharded coverage before applying the existing
floors. See the [parallel CI layout and measured baseline](docs/development/ci-builds.md#parallel-ci-layout-and-measured-baseline)
for the job graph, the historical completed-run timings, and the current status
of the 10-minute PR-wall target. The historical run predates this layout and
does not establish its runtime.

Rust target caches are published only by successful main producers. pnpm store
snapshots also save on main only. Compatible
Linux jobs share dependency keys; native, coverage, and standalone producers
share source-only registry caches instead of duplicating compiled dependencies.
Test shards download producer artifacts rather than saving private target
directories. Cold and restored builds both disable incremental compilation. Bounded retention prunes obsolete main
and closed-PR entries, deduplicates compatible pnpm stores, then evicts the
oldest-accessed main workspace snapshots to fit 8 GiB. Open PRs and unknown
cache families remain protected; their excess is reported. Workspace fallback
keys require the same Cargo configuration to avoid accumulating obsolete
outputs after manifest changes. See [cache capacity and cold-build validation](docs/development/ci-builds.md#cache-capacity-and-cold-build-validation)
for cold/warm measurement inputs and archive provenance checks. Warm validation
still runs every test and collects fresh coverage profiles.
Native compilation diagnostics retain Cargo unit freshness, features, and
profiles. The opt-in shared-target experiment measures runtime-first reuse while
preserving each build graph; see [Cargo unit overlap profiling](docs/development/ci-builds.md#cargo-unit-overlap-profiling).

The coverage test step shares nine raw profiles per instrumented binary through
LLVM's online merge pool. This preserves concurrent subprocess counts without a
full raw profile for every CLI invocation. LCOV, CRAP, and coverage floors still
consume all collected counts. Run `node --test .github/scripts/rust-profile-pooling.test.cjs`
with `llvm-tools-preview` installed to compare pooled and per-process reports.

Before pushing Rust analysis changes, also run the AST invariant checks used by
CI with ast-grep 0.44.1. The repository `check` command does not run these guards;
for example, direct clock calls must go through the optional observer even when
their caller already checks whether diagnostics are enabled.

```sh
ast-grep test --skip-snapshot-tests
ast-grep scan --off=no-inline-test-fixture-write --off=no-inline-test-fixture-write-cfg
analysis_base_ref=$(git merge-base HEAD origin/main)
python3 .ast-grep/check-inline-fixture-writes.py --base "$analysis_base_ref"
```

For mixed Rust/Node changes, run `pnpm run fmt:js:check` after integrating runtime,
declaration and test edits so the aggregate formatter covers every contributor's files.

When moving Rust entrypoint logic, search for `include_str!` source guards and
run those tests alongside the focused module tests.

For shared diagnostics changes, run the full `suite_cli_queries` target to cover
every command's basic timing catalog alongside verbose instrumentation.

Rust integration tests share six explicitly registered suites: `suite_cli_queries`,
`suite_cli_rules`, `suite_cli_postgres`, `suite_cli_package_config`,
`suite_cli_test_plans`, and `suite_contracts`. This links the analyzer once per suite instead of once per
source file. Keep new root `crates/no-mistakes/tests/*.rs` modules registered in
one suite; the registration test rejects omitted or duplicate sources. Original
module and fixture paths stay unchanged. To run one former target, use, for example,
`cargo test --locked -p no-mistakes --test suite_cli_queries cli_queries::`.
Use the full module-qualified name with `-- --exact` for a single test.
`windows_job_object` and `windows_invocation` remain separate platform harnesses in `crates/no-mistakes`,
while `macos_invocation` lives in `crates/no-mistakes-invocation` alongside `src/invocation*` (re-exported by `crates/no-mistakes` as `invocation`). The native macOS job also runs
`cargo test --locked -p no-mistakes --bin no-mistakes invocation::tests::blocked_check::`
for the blocked-check timeout regression. This binary subprocess test opens the
configuration FIFO from the writer side to prove the real check reader reached
config loading, then waits for the parent to arm its one-second production
watchdog. Startup and readiness have their own bounded wait, so coverage startup
load cannot consume the deadline intended for blocked check execution. The parent
also verifies the blocked helper survives longer than its command budget while
the start gate remains closed. It always kills and reaps the helper when readiness
or timeout assertions fail.

Mermaid validation tests require the default `mermaid-validation` feature. The
suites gate only those modules, so other tests remain available without default
features. CI runs `cargo check --locked --tests --no-default-features -p no-mistakes`
to prevent integration tests from importing feature-disabled APIs. Default-feature
Clippy and all-feature validation retain the Mermaid fixture and snapshot tests.

For this repository, use `no-mistakes impacted-checks <changed-file> --root .
--format json` to obtain the configured Rust validation command. The Cargo test
planner currently derives integration target names from source filenames; it
cannot project a changed suite module onto an explicit `[[test]]` target.
Run the returned workspace test command or the suite commands above.
Production Rust changes under `crates/no-mistakes/src/` also select
`cargo test --locked -p no-mistakes --lib architecture` to validate prepared
analysis ownership and canonical graph reuse, even when only a source file changes.

CI runs Rust tests under nextest with `.config/nextest.toml`: a test running
past 60s is named in the log and killed after 10 minutes, so a hang fails fast
and identifies the test instead of exhausting the job timeout.

CI checks links to this repository's `main` documentation against the checked-out
`docs/` files, including new pages in a pull request. Missing targets still fail;
links outside that documentation prefix continue to be checked over the network.

Every native release target uses ThinLTO and 16 code generation units so LLVM
can optimize the combined CLI and N-API build in parallel on a cold runner.
The workflow sets these Cargo profile overrides before restoring its build
cache. A local `cargo build --release` still follows the Cargo.toml release
profile, which is full LTO and one code generation unit, unless those
environment variables are set. Compile-time and runtime differences require
measurements on the same platform.

Linux real-addon cases use isolated jobs and retain serial files within each
job so native thread pools do not compete. The shared file catalog and case
partitioning script keep umbrella imports visible; see the
[Linux API measurements](docs/development/ci-builds.md#linux-real-addon-aggregate-budget-measurement).
Real-addon API tests run in six Windows shards and two macOS shards. Platform
Rust tests run in six Windows shards and four macOS shards. The macOS Rust plan
uses observed outlier weights to balance cases; unknown cases remain included with a default weight. The per-test
timing checks and diagnostic reports
remain in force. The prior serial-test and aggregate timeout measurements are
historical; the [CI build guide](docs/development/ci-builds.md#parallel-ci-layout-and-measured-baseline)
records the earlier baseline, completed parallel measurements, and the cache
and runner-capacity limits that still prevent the ten-minute target.

Pull requests run the validation jobs for Markdown changes as well as code
changes. Documentation contract tests are part of the Rust coverage build and
the required `Docs tests` check runs documentation tests independently. The
docs-only path detector does not skip that non-macOS matrix. macOS native
build, compile, Rust test, and API test jobs run on a pull request only when
the diff can differ on macOS: native bindings, platform packages, Cargo
manifests, the toolchain file, build scripts, path and filesystem modules, or
CI workflows. A docs-only or postgres-rule-only pull request skips those jobs.
The pull request diff starts at the merge base with the base branch, so a
workflow edit that exists only on the base does not count. `Tests with coverage`
treats that skip as success. Pushes to
`main` and the release workflow always run the macOS jobs. Markdown under
`crates/`, `packages/`, `plugins/`, `fixtures/`, `test-cases/`, `tests/`,
`evals/`, `.ast-grep/`, and `docs/eslint-rules/`, plus pages read by unit and
package tests, remains test input; update the docs-only detector tests when
adding new test-read pages.

## Shared machines and memory

Release builds, full-workspace tests, `cargo llvm-cov`, and Criterion each use a
large share of RAM and spawn many processes. Several agents running them at once
can exhaust memory and hang the machine until a hard reset. When agents share a
machine:

- Run heavy jobs one at a time, behind a machine-wide lock or a memory- and
  task-capped scope, with a limited `CARGO_BUILD_JOBS`. A lock alone does not
  cap one job's memory.
- Prefer CI for coverage. Never `eval "$(cargo llvm-cov show-env)"` in a working
  shell; every later cargo command in that shell is instrumented.
- Run focused tests (`-p <crate>`, `--test <suite>`, a name filter) before the
  full suite.
- Check available memory before starting a heavy job.
- Keep worktrees and target directories where a reboot will not delete them,
  and commit and push early so a crash loses no work.
- Delete throwaway target directories as soon as they are no longer needed.

The pre-push hook accepts Cargo's usual `CARGO_TARGET_DIR`. Use one private
target for a worktree's local validation and pushes so Cargo can reuse matching
inputs. Running the hook's exact Clippy command locally warms the same cache
when the profile, features, and environment match.

A lane can hand its private target from a retired checkout to a successor.
Wait for the old checkout's Cargo processes to finish and keep the target's
absolute path. Before removing the old worktree, run the following **from the
old checkout** with the lane's existing target.

```sh
: "${CARGO_TARGET_DIR:?set the lane's absolute target path}"
cargo clean --locked --workspace --target-dir "$CARGO_TARGET_DIR"
```

This removes workspace outputs so Cargo checks the successor's own sources.
Registry dependency artifacts remain available. Use a fresh private target
when the old workspace had extra local path dependencies, used a separate
build directory, or cannot be cleaned. Each active lane keeps its own target.

## Deprecations

Before deprecating a command, compare every supported input, option, scope, and
report capability with its proposed replacement. Keep a surface maintained when
its replacement cannot answer the same query, and record the gap in the PR and
migration page. Removal requires a separate change; deprecation does not disable
commands, rules, exports, or existing configurations.

- Keep analysis results, CLI reports, lint findings and severity, options, and
  exit codes unchanged.
  A deprecated CLI command writes one best-effort warning line to stderr from
  its dispatch boundary, naming the replacement or stating that none exists.
  Never add the warning to stdout or a JSON report, and never fail because the
  warning could not be written. Help and argument parsing retain their normal
  behavior before command dispatch.
- Mark the matching Node API function in the CommonJS/ESM facades and `.d.ts`
  export with `@deprecated`. Keep invocation behavior unchanged; do not add
  runtime logging to Node calls. Document the canonical batched report type.
- For ESLint rules, use native `meta.deprecated` with a message and replacement
  information (`replacedBy: []` when none exists). Do not add a lint finding,
  alter diagnostics, or use process-global warning state. ESLint owns
  `usedDeprecatedRules` result metadata and its presentation; plugins have no
  per-invocation stderr hook. Document that metadata exception to JSON parity.
- Open each deprecated page with its status and replacement. Route active
  indexes and the packaged agent skill to maintained surfaces. Keep deprecated
  entries in labeled compatibility lists and in the complete Node runtime
  export inventory. Add a migration page explaining all affected surfaces.
- Use saved-fixture regressions to compare CLI stdout and exit status with the
  maintained equivalent, assert one stderr warning, and cover error exits.
  Keep lint diagnostic snapshots unchanged; test host deprecation metadata and
  disabled-rule controls. Lock declaration annotations in the API tests.

See [the initial surface migration](docs/migrations/deprecated-surfaces.md).

## Pull request descriptions

A reader must be able to tell from the pull request description what the change
does on a realistic input; that is how a wrongly built feature gets caught.

For each behavior the pull request changes, include:

- the problem,
- a real input (a saved fixture, with its path),
- the exact `no-mistakes` command (or test command for CI and test-only changes), and
- the full real output before (`main`) and after.

A checklist or table of case names, elided output (`...`), CI links in place of
output, or a diff summary alone does not count. Rewrite the description whole
when the pull request changes rather than appending to it.
