# Contributing

This repository is a huge token sink. Thus, contributions are welcomed.

1. Please add test cases as files on disk, never built inside a test:
   - New scenarios go in `test-cases/<category>/<scenario>/fixture/`. Rule pass/fail pairs go in
     `test-cases/rules/<rule>/fixture/{pass,fail}`.
   - A suite whose loader reads `fixtures/<category>/<name>/` (benchmarks, N-API, test-plan, and
     some per-rule cases) keeps its cases there. Both trees hold some `rules/`, `lockfile/`, and
     `check-runner/` cases, so find the suite's loader with `rg` and add to the tree it reads.
   - Crate-local resolver, source-discovery, and workspace cases live in readable,
     named directories under `crates/no-mistakes/fixtures/`. Load them with
     `crate::test_support::fixture_root`; use `materialize_saved_fixture` for an
     isolated copy before mutating files or initializing Git.

   Catalog rules listed in `SCHEMA_CATALOG_RULE_IDS` also update
   `fixtures/postgres/catalog-generation/all-rules/.no-mistakes.yml` and
   `schema.sql`, then regenerate that directory's `schema.json` on PostgreSQL 18
   (omit only the generated `currentDatabase` line). Add compliant and reported
   controls. With `NO_MISTAKES_TEST_POSTGRES_URL` set, run
   `cargo test --locked -p no-mistakes --test suite_cli_postgres postgres_catalog_real::rules`
   as well as the rule's own snapshots; the catalog inventory, generated bytes,
   complete-coverage requirement, and every-rule behavior are separate gates.

Fixture visibility must agree in Git checkouts and extracted release archives. Do not
rely on a force-tracked file overriding `.gitignore` for a shared CLI snapshot.
Keep deliberately hidden-source controls separate, and exercise fixture
materialization without Git when discovery behavior matters. Installed-package fixtures may
remain ignored by source discovery while their committed files are copied intact.

2. Rule output tests commit file snapshots. Review `.snap` and Vitest file-snapshot
   diffs like code. Rust `check --format json` snapshots use
   `crates/no-mistakes/tests/common/check_json_snapshot.rs`, which compares `--jobs 1`
   with `--jobs 2` and rewrites absolute paths, temp directories, process ids, and
   timings so the file is stable on Linux, macOS, and Windows. Each finding with a
   `file` and `line` also gets `sourceLine`, the trimmed text of that fixture line
   (LF, no absolute paths; absent when the file is not a readable fixture file), so a
   finding on the wrong line shows up in the snapshot diff. CI sets `INSTA_UPDATE=no`
   and fails when a snapshot is missing or changed. The shared full Rust test
   command (`bash .github/scripts/rust-validation.sh test`) also collects
   executed snapshot references and rejects orphan `.snap` files in workspace
   packages. Remove obsolete snapshots when deleting or renaming their tests;
   filtered test runs cannot establish the full reference inventory.
   Text-format coverage for
   `agents-md-max-size` moved into that JSON snapshot: the empty pass, the
   over-limit message, the rule id, and the disabled skip. Regenerate on purpose with
   `INSTA_UPDATE=1 cargo test -p no-mistakes --test suite_cli_rules check_json_snapshot`
   or `cargo insta review`. In `packages/eslint-plugin-no-mistakes`, fixture
   diagnostics use Vitest `toMatchFileSnapshot` with relative paths and sorted
   findings. CI does not pass `-u`. Update with `pnpm exec vitest run <test> -u`
   only when that output change is intended.
3. Annotate which AI harness + model was used, `Co-Authored-By` is preferred
4. Maintain 98% project and patch test coverage

Development, CI, release builds, and benchmarks use the latest stable Rust.
Run `rustup update stable` before local validation; `rust-toolchain.toml` selects
that channel and installs Clippy and rustfmt. Workflows select `toolchain: stable`
while pinning the setup action code separately. Benchmark comparisons must use
the same resolved compiler version for both runs and record that version.

After a stable toolchain update, validate library and test targets with
`cargo clippy -p no-mistakes --all-targets -- -D warnings`, using the shared-machine
limits below. Command tests should assert their expected `ExitCode`. Preserve
short-circuit evaluation and token positions when simplifying predicates or
replacing indexed loops, then replay the affected saved fixtures and snapshots.

CI enforces per-function CRAP and cyclomatic complexity limits of 30. The
complexity gate runs `cargo crap --workspace --missing optimistic --fail-above
--threshold 30 --summary` without LCOV: assuming full coverage makes CRAP equal
cyclomatic complexity, including source omitted from the coverage report.

The optimistic check does not replace the coverage-aware CRAP gate. After a
crate-scoped coverage run, export LCOV and check the changed crate:

```sh
cargo llvm-cov report --lcov --output-path /tmp/no-mistakes-lcov.info
cargo crap -p no-mistakes --lcov /tmp/no-mistakes-lcov.info --missing skip --fail-above --threshold 30
```

Conditional framework dispatch needs fixture coverage for every supported branch,
even when its cyclomatic complexity is below 30.

Check coverage of added lines separately from whole-project coverage. Passing the
project floor does not establish the Codecov patch floor; inspect the changed
lines in LCOV and cover error diagnostics with saved invalid fixtures before
handoff. Wait for the patch check to finish after the workflow coverage job passes.

Run `pnpm run lint:duplicates` to check for copied blocks of at least 30 lines
and functions with at least 80% structural similarity. CI runs the same jscpd
check and fails on any reported clone. See the [duplication guide](docs/development/code-duplication.md)
for its scope and how to fix findings.

Native CI builds and platform tests omit Rust debug metadata to keep compilation
within their ten-minute step deadlines. Development and test profiles use the same
setting so Windows can reuse the CLI's library build. Debug assertions stay enabled;
Linux still runs the full suite and enforces the coverage gates. These defaults
live in the workspace Cargo profiles, including release validation. For local
debugging, use `CARGO_PROFILE_DEV_DEBUG=2` or `CARGO_PROFILE_TEST_DEBUG=2`.

CI and release validation share `.github/scripts/rust-validation.sh`: `build` and
`test` select the locked workspace, all features, libraries, binaries, and integration
tests; `doc` runs documentation tests separately. Coverage instrumentation stays scoped to
the coverage build and test steps. Run the shared script locally with Bash to
reproduce either validation scope. Release resumes use validation tooling from
the running workflow while retaining the tagged Rust source; see the
[CI build guide](docs/development/ci-builds.md).

The coverage test step shares nine raw profiles per instrumented binary through
LLVM's online merge pool. This preserves concurrent subprocess counts without a
full raw profile for every CLI invocation. LCOV, CRAP, and coverage floors still
consume all collected counts. Run `node --test .github/scripts/rust-profile-pooling.test.cjs`
with `llvm-tools-preview` installed to compare pooled and per-process reports.

Before pushing Rust analysis changes, also run the AST invariant checks used by
CI with ast-grep 0.44.1. The repository `check` command does not run these guards;
for example, direct clock calls must go through the optional observer even when
their caller already checks whether diagnostics are enabled.

```sh
ast-grep test --skip-snapshot-tests
ast-grep scan --off=no-inline-test-fixture-write --off=no-inline-test-fixture-write-cfg
analysis_base_ref=$(git merge-base HEAD origin/main)
python3 .ast-grep/check-inline-fixture-writes.py --base "$analysis_base_ref"
```

For mixed Rust/Node changes, run `pnpm run fmt:js:check` after integrating runtime,
declaration and test edits so the aggregate formatter covers every contributor's files.

When moving Rust entrypoint logic, search for `include_str!` source guards and
run those tests alongside the focused module tests.

For shared diagnostics changes, run the full `suite_cli_queries` target to cover
every command's basic timing catalog alongside verbose instrumentation.

Rust integration tests share five explicitly registered suites: `suite_cli_queries`,
`suite_cli_rules`, `suite_cli_postgres`, `suite_cli_test_plans`, and
`suite_contracts`. This links the analyzer once per suite instead of once per
source file. Keep new root `crates/no-mistakes/tests/*.rs` modules registered in
one suite; the registration test rejects omitted or duplicate sources. Original
module and fixture paths stay unchanged. To run one former target, use, for example,
`cargo test --locked -p no-mistakes --test suite_cli_queries cli_queries::`.
Use the full module-qualified name with `-- --exact` for a single test.
`windows_job_object` and `macos_invocation` remain separate platform harnesses
for their process and crate-root requirements. The native macOS job also runs
`cargo test --locked -p no-mistakes --bin no-mistakes invocation::tests::blocked_check::`
for the blocked-check timeout regression. This binary subprocess test opens the
configuration FIFO from the writer side to prove the real check reader reached
config loading, then waits for the parent to arm its one-second production
watchdog. Startup and readiness have their own bounded wait, so coverage startup
load cannot consume the deadline intended for blocked check execution. The parent
also verifies the blocked helper survives longer than its command budget while
the start gate remains closed. It always kills and reaps the helper when readiness
or timeout assertions fail.

Mermaid validation tests require the default `mermaid-validation` feature. The
suites gate only those modules, so other tests remain available without default
features. CI runs `cargo check --locked --tests --no-default-features -p no-mistakes`
to prevent integration tests from importing feature-disabled APIs. Default-feature
Clippy and all-feature validation retain the Mermaid fixture and snapshot tests.

For this repository, use `no-mistakes impacted-checks <changed-file> --root .
--format json` to obtain the configured Rust validation command. The Cargo test
planner currently derives integration target names from source filenames; it
cannot project a changed suite module onto an explicit `[[test]]` target.
Run the returned workspace test command or the suite commands above.
Production Rust changes under `crates/no-mistakes/src/` also select
`cargo test --locked -p no-mistakes --lib architecture` to validate prepared
analysis ownership and canonical graph reuse, even when only a source file changes.

CI checks links to this repository's `main` documentation against the checked-out
`docs/` files, including new pages in a pull request. Missing targets still fail;
links outside that documentation prefix continue to be checked over the network.

ARM macOS release builds use ThinLTO and 16 code generation units so LLVM can
optimize the combined CLI and N-API build in parallel on a cold runner. The
workflow sets these Cargo profile overrides before restoring its build cache.
Other release targets and local builds retain full LTO and one code generation
unit. Compile-time and runtime differences require measurements on the same
platform; Linux benchmarks do not establish the macOS tradeoff.

Native API tests run serially on Windows and macOS. Their CI step allows seven
minutes on Windows and five on macOS; individual test deadlines and duration
warnings remain in force. The native job retains its thirty-minute limit.
Saved timing records distinguish historical censored progress from current
completed setup and Rust work; neither observation guarantees tail duration.

Pull requests that change only Markdown run `Docs tests` (the `suite_contracts`
docs checks) instead of the full test jobs. Quality and AST analysis still run,
and pushes to `main` run everything. Markdown under `crates/`, `packages/`,
`plugins/`, `fixtures/`, `test-cases/`, `tests/`, `evals/`, `.ast-grep/`, and
`docs/eslint-rules/`, plus the pages that unit and package tests read, is test
input and runs the full suite. `.github/scripts/docs-only-scope.cjs` owns the
list, and `tests/js/docs-only-scope.test.js` fails when a test reads a page
missing from it.

## Shared machines and memory

Release builds, full-workspace tests, `cargo llvm-cov`, and Criterion each use a
large share of RAM and spawn many processes. Several agents running them at once
can exhaust memory and hang the machine until a hard reset. When agents share a
machine:

- Run heavy jobs one at a time, behind a machine-wide lock or a memory- and
  task-capped scope, with a limited `CARGO_BUILD_JOBS`. A lock alone does not
  cap one job's memory.
- Prefer CI for coverage. Never `eval "$(cargo llvm-cov show-env)"` in a working
  shell; every later cargo command in that shell is instrumented.
- Run focused tests (`-p <crate>`, `--test <suite>`, a name filter) before the
  full suite.
- Check available memory before starting a heavy job.
- Keep worktrees and target directories where a reboot will not delete them,
  and commit and push early so a crash loses no work.
- Delete throwaway target directories as soon as they are no longer needed.
